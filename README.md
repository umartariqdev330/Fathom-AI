# Meetly AI

An AI meeting notetaker, built as a 24-hour rebuild of [fathom.video](https://fathom.video).

Meetly records a call, transcribes it, and turns it into something you can actually
use afterwards: a synced transcript, an AI summary, action items, highlights, search
across every meeting you have ever recorded, and a public clip link you can send to
someone who was not on the call.

**The capture layer is simulated.** The brief allows it, and the interesting product
is on the other side of the recording. See [What is simulated](#what-is-simulated).

---

## Try it in 60 seconds

1. Open the dashboard. Eight recorded meetings and five upcoming ones are already there.
2. Open **AI Platform Architecture Review** — eight people, 58 minutes. This is the hard
   case the brief asks about.
3. Press play. The transcript follows along. Click any line and the recording jumps there.
   Switch the summary template to **Sales call** or **Engineering review** and watch the
   sections change.
4. Click a coloured dot on the timeline — those are highlights.
5. Hit **Share clip**, create it, open the link. It works signed out, in a private window.
6. Search `pgvector`, or `redaction`, or `Priya`. Results land on the exact moment.

A permanent share link is seeded at **`/share/demo-clip`**.

## Features

**Meeting detail** — the centre of the product. Player, AI summary, action items and
highlights on the left; the transcript locked in a rail beside them, never below the fold.
Clicking a transcript line seeks the recording; playing the recording moves the transcript
and highlights the active line. Highlights render as markers on the timeline.

**Transcript** — speaker-attributed and timestamped, searchable within the meeting with
match highlighting and a match count, copy and download to a text file, and a star on any
line to turn it into a highlight.

**AI summary with switchable templates** — overview, key points, decisions, topic tags and
AI insights. Five templates re-read the same meeting through a different lens: General,
Sales call, Engineering review, One-on-one and Product review. Switching template changes
the sections *and* their content, because each one is regenerated from the transcript
rather than relabelled. Generated by an LLM when a key is configured, and by cue-based
extraction from the transcript when it is not — in which case every point is a quoted
transcript line you can click to play, so its timestamp is exact rather than inferred.

**Action items** — assignee, due date, status. Check one off and it updates immediately.
Add, edit and delete inline.

**Highlights** — four categories (key moment, decision, risk, insight), each with the
transcript excerpt it came from. Play from the exact moment, or turn one into a shareable
clip in two clicks. A cross-meeting highlights page filters by category.

**Search** — one query across transcripts, titles, summaries, action items, highlights and
participants. Results group by meeting, show which surface matched, and deep-link to the
timestamp.

**Clip sharing** — pick a range, name it, get a link. The share page is public, needs no
account, and carries the clip's own transcript.

**Calendar** — upcoming and past meetings, with a simulated Google/Outlook connection flow.

**Simulated recording** — choose a platform, record, stop, watch the pipeline run, land on
a finished meeting. The summary on that meeting is genuinely generated at that moment.

Plus: light and dark themes, keyboard focus states throughout, `Cmd/Ctrl+K` to search,
loading skeletons, empty states, toast feedback, and a layout that works from 375px up.

## Architecture

```
backend/                 FastAPI + SQLAlchemy + SQLite
  app/
    api/                 one router per resource
    models.py            SQLAlchemy models
    schemas.py           Pydantic request/response types
    services/ai.py       LLM summarisation with a local fallback
    seed/                one module per seeded meeting
    main.py
  seed.py                rebuilds the database from app/seed/

frontend/                React + TypeScript + Vite + Tailwind
  src/
    components/          UI primitives, layout, meeting/ panels
    pages/               one per route
    hooks/usePlayer.ts   playback transport
    lib/api.ts           typed API client
    types.ts             shared types, mirroring the API schemas
```

The database is SQLite so the project runs with no setup. Nothing depends on SQLite
specifically — set `DATABASE_URL` to a Postgres URL and it works unchanged.

Seed content lives one meeting per module because it is prose, not configuration, and
prose is easier to read and edit when each meeting stands alone.

### How highlights stay on the right line

Transcript timestamps are generated from speaking pace, so hand-written timestamps drift
as soon as any wording changes. Seeded highlights are therefore anchored to a **quote**
from the line they refer to, and the seeder resolves that to a real time. If a quote stops
matching, seeding fails loudly instead of shipping a highlight that plays the wrong moment.

## AI

`backend/app/services/ai.py` exposes two functions: `summarise(title, segments)` for a
meeting's own summary, and `apply_template(title, segments, template)` for reading it back
under one of the templates in `services/templates.py`.

- **With `OPENAI_API_KEY` set** — the transcript goes to the model and comes back as
  structured JSON: overview, key points, decisions, topics, insights, action items. For a
  template, the model is asked for exactly that template's headings.
- **Without a key** — the transcript is processed locally: longest contributions as key
  points, phrase matching for decisions and action items, term frequency for topics. For a
  template, each section pulls the transcript lines matching its cues, which is why those
  points are quotes with exact timestamps rather than paraphrases.

If the API call fails for any reason, the fallback runs instead. The product never breaks
because an external service is unreachable, and it never requires a key to be useful. The
summary panel states which path produced what you are reading.

The eight seeded meetings ship with hand-written summaries, so the demo shows the quality
a good model produces rather than the quality of the fallback. The fallback is what you
see on a meeting you record yourself through the simulated flow.

## What is simulated

| Simulated | What is real |
|---|---|
| The recording bot joining a call | The meeting record it produces: transcript, summary, action items, participants |
| Audio and video capture | The playback transport, at the meeting's real duration, driving transcript sync |
| Google/Outlook OAuth | The connection flow, endpoint, and connection state |
| Accounts and auth | Nothing is gated, and the public share route is genuinely public |

**Why capture is stubbed.** A bot that reliably joins Zoom, Meet and Teams is days of work
and an infrastructure problem, not a product one. The brief says it can be stubbed. Every
hour spent on it is an hour not spent on the part of Fathom people actually live in, which
is everything that happens after the call ends.

**On playback.** Because there is no recording, the player is a virtual transport rather
than a `<video>` element. That was a deliberate choice over dropping in a stock clip: a
15-second sample against a 58-minute transcript makes every timestamp a lie, and transcript
sync — the thing worth demonstrating — stops working. Instead the stage shows who is
speaking and what they are saying as the clock advances, which is honest and, for a
notetaker, more useful than a video thumbnail.

## Local setup

Two terminals. Python 3.11+ and Node 18+.

**Backend**

```bash
cd backend
pip install -r requirements.txt
python seed.py
uvicorn app.main:app --reload --port 8000
```

**Frontend**

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. Vite proxies `/api` to the backend, so no environment
variables are needed for local development.

API docs are at http://localhost:8000/docs.

---

## Environment variables

Copy `.env.example` to `.env` in `backend/`, and to `.env.local` in `frontend/` if needed.

| Variable | Where | Required | Purpose |
|---|---|---|---|
| `DATABASE_URL` | backend | no | Defaults to SQLite. Accepts a Postgres URL. |
| `OPENAI_API_KEY` | backend | no | Enables LLM summaries. Without it the fallback runs. |
| `OPENAI_MODEL` | backend | no | Defaults to `gpt-4o-mini`. |
| `CORS_ORIGINS` | backend | in production | Comma-separated list of allowed origins. |
| `VITE_API_URL` | frontend | in production | The deployed API origin. Empty in development. |

No secrets are committed.

## Deployment

The two halves deploy independently.

**Backend** — `render.yaml` is included. Point Render at the repo, and set `CORS_ORIGINS`
to the deployed frontend origin. The API seeds itself on first boot if its database is
empty, so a fresh deploy is never an empty workspace.

**Frontend** — `frontend/vercel.json` is included, with the SPA rewrite that keeps
`/share/:token` working on a hard refresh. Set `VITE_API_URL` to the deployed API origin
and deploy `frontend/`.

Check after deploying: the live link opens in a private window, and a share link opens
signed out.

## Product decisions

**What I built first, and why.** Meeting detail, before anything else. It is where the
product is used and where a rebuild either feels real or does not. The dashboard, calendar
and settings pages came last, because they are navigation around the thing rather than the
thing.

**Seed data was treated as a feature, not filler.** Eight meetings with 234 transcript
segments, written as real conversations with a continuing cast and a storyline that runs
across them: a summarisation bug found in one meeting drives a roadmap decision in another,
gets estimated in sprint planning, and is disclosed to investors. Lorem ipsum would have
cost less and shown nothing. The evaluator reads this content, so it had to be worth
reading, and cross-meeting search is only interesting if the corpus has something in it.

**What I deliberately left out.**

- *Citations on the seeded General summary.* Template-generated sections **do** cite exact
  timestamps, because each point is a quoted transcript line. The hand-written General
  summary does not, because its points are paraphrases: carrying citations through properly
  needs the summariser to keep segment ids, and fuzzy-matching paraphrases back to lines
  produces confident jumps to the wrong moment. A wrong citation is worse than none.
- *Semantic search.* Keyword search across everything ships and is useful. Embeddings plus a
  vector index is a week, not an afternoon.
- *Accounts, teams, permissions.* Nothing here is improved by a login screen, and the share
  page is more convincing without one.
- *A real recording bot,* for the reasons above.
- *Redaction, shared highlights, CRM integrations.* Real customer needs in the seeded
  conversations, deliberately out of scope for one day.

**Where I would go next**, in order: summary citations with segment ids carried through the
pipeline; chunked summarisation so long meetings do not degrade; semantic search; then
shared highlights, which the seeded customer interview argues is the highest-leverage thing
the product is missing.
